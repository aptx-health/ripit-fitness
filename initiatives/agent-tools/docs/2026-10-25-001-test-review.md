# Review: agent-proposal tests (work item 001)

**Your call:** accept 001 as is, or ask for the test fixes below first. My recommendation is to accept and fix #1 and #2 in a small follow-up. Neither blocks the implementer.

Status as of 2026-10-25 20:34 MDT: **all 17 scenarios are red**, each failing because the code doesn't exist yet. That's the correct state before implementation. The lead re-ran the suite to confirm.

Shared setup for every scenario:
- Dustin and one other user exist.
- Dustin has an agent token named "mac-claude".
- Dustin owns a "Barbell Bench Press" with the alias "bench" and the notes "Original notes".

## Tokens

**A valid token identifies Dustin.** Checks that the token resolves to Dustin and this token, that last-used is set, and that the database stores only a SHA-256 hash, never the token itself.

**A revoked token is refused.** Marks the token revoked, then checks that it resolves to nobody and that last-used stays empty.

**No self-approval tool.** Lists the tools and checks that both propose tools are there and that no tool name contains approve, reject, revert, decide, apply or undo.

## Reading data

**Search.** Searches for "bench" and checks that the result contains Bench Press's name and id.

**Workout history.** Seeds one completed workout for Dustin with 3 logged sets and one for the other user with 2. Checks that the result has Dustin's workout and exactly 3 sets, and that it has none of the other user's workout name, completion id or user id.

## Proposing

**New exercise.** Proposes "Larsen Press" (barbell, chest and triceps). Checks:
- The proposal is pending, of kind create, and owned by Dustin and this token.
- It keeps the rationale and has no decision time yet.
- Larsen Press is not in the library.
- Exactly one notification was sent.

**Invalid muscle group.** Checks that the tool errors and names `primaryFAUs`, that no proposal row exists and that no notification was sent.

**Duplicate.** Proposes "Barbell Bench Press" again. Checks that it errors with the existing exercise's id and that no proposal is created.

**Bark down.** Notify throws. Checks that the tool still succeeds without throwing and that a pending proposal exists.

## Deciding

**Approve a create.** Checks that Larsen Press now exists, is owned by Dustin and has the right equipment and muscle groups, and that the proposal is applied with a decision time and undo data.

**Approve an update.** Checks that only `notes` changed. Every other field of Bench Press is compared before and after.

**Stale update.** The notes are edited directly after the proposal is made. Checks that the proposal becomes `conflict` and that the later edit survives.

**Reject.** Checks that the proposal is rejected with a decision time and that Larsen Press doesn't exist.

**Approve twice.** Checks that the second approve errors mentioning "pending", that the status stays applied and that there is still exactly one Larsen Press.

## Undo

**Revert an update.** Checks that the notes are back to "Original notes" and the status is reverted.

**Revert an unused create.** Checks that Larsen Press is gone and the status is reverted.

**Revert a create that's in use.** Larsen Press is added to one of Dustin's workouts. Checks that the revert errors ("in use", "used" or "referenc"), that Larsen Press still exists and that the status stays applied.

## Weak spots (observed in the test code)

1. **The Bark link isn't checked.** The test only checks that the notification contains the proposal id. The spec now pins `url` as `.../admin/proposals/<id>`, but the test was written before that. *Suggest a fix.*
2. **Error shapes are loose.** Because the spec was silent, the tests accept a thrown error or any of four "failed" return shapes. The spec now pins `{ ok: false, code }` for services and `isError` for tools. *Suggest a fix, so the tests enforce `code`.*
3. **The stale test checks only the outcome.** It verifies the `conflict` status and the surviving edit, but not that approve reported an error. This is minor.
4. **Some steps pass early.** While red, some steps already pass, for example "not in library" while nothing exists. A scenario only counts as green when all its steps pass, so this is harmless.
